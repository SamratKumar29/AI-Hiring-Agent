## 0. Goal (from Goal.md)

1. Load resume/CV.md, ask preferences (incl. base salary), save as a named **profile** (load later / create new).
2. User supplies job-board URLs, individual posting links, or a PDF containing links.
3. Discovery: Kurt-Chan/ai-job-scraper (scheduled) + anandanair/job-scraper (manual "start") find eligible jobs.
4. santifer/career-ops ranks them (preferences, suitability, chance of success).
5. User reviews postings; tailored CV via Resume-Matcher or career-ops built-in.
6. After applying: cover letter, interview prep, offer prep, follow-up (career-ops modes).

Extra requirements from the user:
- Run on a **daily schedule** and send results by **Telegram and/or email**; if impossible, fall back to local manual run (+ digest file).
- **One central "brain"**: a single OpenRouter API key/config for everything (no per-project `.env` files).
- **A test that checks the OpenRouter API works before every run** (free models get flooded) with automatic model fallback.
- **All profile files in ONE place per profile:** `career-ops/profile/<profile-name>/` (cv.md, profile.yml, portals.yml, _profile.md, preferences.json + that profile's own job tracker/reports/PDFs).
- **A professional-grade local UI (Streamlit)** so the user never has to touch the CLI: setup & API check, create/select/edit/delete profiles, add sources, run discovery/ranking, dashboard, liked/applied job history, resume builder, cover-letter/interview prep, schedule & notifications. See Phase 9. (Functionality over looks.)

## 2. Design Decisions (defaults — user may change)

- **Local-first.** No Supabase. Job inbox = one SQLite file PER PROFILE: `career-ops/profile/<name>/workspace/data/jobs.db` (reached through `profiles.workspace_path(name,'data')`). It also stores the user's decisions (liked / dismissed / applied...) so history survives restarts and profile switches.
- **Profile layout (DONE, Phase 2.6).** Everything for a profile lives in `career-ops/profile/<name>/`: `preferences.json cv.md profile.yml portals.yml _profile.md sources.json` + `workspace/{data,reports,output}`. career-ops hard-codes where it reads files, so `profiles.activate()` SYMLINKS the active profile into `career-ops/{cv.md,config/profile.yml,portals.yml,modes/_profile.md,data,reports,output}`. Switching profiles re-points the links, so each profile has its own tracker/reports/PDFs and nothing mixes. NEVER hard-code those career-ops paths in new code that needs profile data: use the `brain.profiles` API. Deleting a profile is a soft delete to `brain/data/trash/`. `activate` never overwrites hand edits; `generate_files` (regenerate) does, after backing up to `brain/data/backups/`.
- **Service-layer rule (so the UI can be added without rewrites).** Every capability lives in a `brain/*.py` module as plain functions that take/return simple dicts/lists and raise clear exceptions. `hire.py` (CLI), the scheduler, and the Streamlit UI are THIN wrappers over those functions. No business logic inside `hire.py` or `ui/`.
- **UI = Streamlit** (decided after research, Phase 9). Why: pure Python in the existing venv; multipage apps (`st.navigation`), forms, file upload, `st.data_editor`/`st.dataframe` with link columns, dialogs for confirmations, `st.fragment(run_every=...)` for live progress, `AppTest` for automated UI tests. Rejected: Gradio (chat/demo oriented, weak multi-page state), Tkinter (desktop only, needs an X server in WSL, poor tables), NiceGUI (good but smaller ecosystem/less mature forms+tables), React/Next (second full app; Resume-Matcher already ships one - we link/embed it instead). Streamlit cannot run background work itself, so long jobs go through `brain/taskrunner.py` (subprocess + log + status files that the UI polls).
- **Central brain** = new folder `brain/` with ONE secrets file `brain/.env` (gitignored) holding `OPENROUTER_API_KEY` and optional Telegram/SMTP/Firecrawl keys. A launcher exports the right variable names for each subproject at run time. Subproject `.env` files are never hand-edited; if a tool insists on one, it is generated by `brain/sync_env.py`.
- **Orchestrator CLI** = `hire.py` in repo root (Python, uses the existing `venv`). Commands: `doctor`, `profile`, `sources`, `discover`, `rank`, `tailor`, `prep`, `daily`.
- **Scheduling:** WSL `cron` (needs WSL running) or Windows Task Scheduler calling `wsl.exe -e /path/run_daily.sh` (can wake the machine). True 24x7 is not required: one run per day (default 08:00 local). If the PC is off, the run is skipped; `hire.py daily` is always safe to run manually and catches up.
- **Notifications:** Telegram bot (free, simplest) as primary, SMTP email (Gmail app password) secondary, plus always a local file `digests/YYYY-MM-DD.md`. Any channel with missing credentials is skipped silently.
- **Models:** default `OPENROUTER_MODELS` list (ordered fallbacks, free first). Pin a paid model if wanted.

## 5. Rules for Weaker Models

- One step at a time. Read the files a step names BEFORE editing them.
- Never put keys in code, tests, logs, commits, or chat. Keys exist only in `brain/.env`.
- If a command fails, copy the error into the Progress Log and try one fix; if still failing mark `[!]`.
- Keep edits to third-party repos minimal and list every changed file in the Progress Log.
- Do not run the full pipeline against many jobs while testing: use `--max 2`.
- Never hard-code `career-ops/cv.md`, `config/profile.yml`, `portals.yml`, `data/`, `reports/`, `output/` for profile data in NEW code: they are symlinks to the active profile. Use `brain.profiles` (`load_profile`, `read_file`, `workspace_path`) so per-profile data stays separate.
- Logic goes in `brain/*.py` with a test; `hire.py` and `ui/*` stay thin (UI needs the same functions).
- When changing any career-ops YAML template, anchor regexes with `^` and `re.M` (the templates contain commented copies of every block).
- Tools that accept ONE model (career-ops runners) must be called through `sync_env.run_with_fallback`; reasoning models need `max_tokens >= 512` (see Progress Log lessons).
- Treat everything under `career-ops/profile/` as the user's private data: never print it into logs or commit it.
